# Stage 1 — CI quality and supply-chain gates (CI-01…CI-04)

Part of the enterprise roadmap. Goal: every push and pull request is linted, type-checked,
tested with a coverage floor, scanned for vulnerabilities and secrets, and built into a
container image that is itself scanned and described by an SBOM. Nothing is deployed or
published by these workflows.

## What runs where

| Workflow | Job | Checks | Blocks merge? |
|---|---|---|---|
| `ci.yml` | Lint and types | `ruff check` (pyflakes, pycodestyle, isort, bugbear, bandit `S`, blind-except), `mypy` on `app/` and `scripts/` | yes |
| `ci.yml` | Tests and coverage | `pytest --cov`; fails below **90 %** branch coverage of `app/` (measured: 95 %) | yes |
| `ci.yml` | Container image | multi-stage build, smoke test (`/healthz`, runs as uid 10001), Trivy image scan (fixed HIGH/CRITICAL), CycloneDX SBOM artifact | build + smoke: yes; scan: report-only |
| `security.yml` | SAST, deps, secrets, config | Semgrep (`p/python`, `p/flask`, `p/secrets`), pip-audit on `requirements.lock`, gitleaks over full git history, Trivy config/secret scan; SARIF → Security tab | report-only |

`security.yml` also runs every Monday, so a new CVE in an unchanged dependency is noticed.

### Report-only period

`REPORT_ONLY: "true"` in `security.yml` and in the `image` job of `ci.yml`. Scanners run and
publish results, but findings do not fail the build. **Review on 2026-12-01**: look at the
Security tab and the run summaries, fix or suppress (with a reason) what is there, then set
both to `"false"`.

Baseline when the gates were added (2026-11-17): Semgrep 0, pip-audit 0, gitleaks 0,
Trivy config 0, Trivy image 0 after the OS-package upgrade below (before it: zlib
CVE-2026-85091, HIGH).

## CI-01 — lint, types, coverage, pre-commit

- Config lives in `pyproject.toml` (`[tool.ruff]`, `[tool.mypy]`, `[tool.coverage]`).
- Line length 130, `E501` not enforced; the formatter is **not** enforced yet so two people
  editing the same files don't get large reformat diffs. Adopt `ruff format` in one
  separate commit when both branches are merged.
- `S608` (SQL built from strings) was reviewed site by site: every case interpolates only
  `?` placeholders, a fixed column list, or one of two literals. Each has a `noqa` with
  the reason; `stats.py` is exempted in config with a comment.
- Code fixes made for the checks: explicit `zip(strict=…)`, no `l` variable names,
  `storage._rowid()` instead of `int(cursor.lastrowid)`, `verdict_for()` returns the
  `Verdict` literal type, `redirect()` never gets `None`.
- `.pre-commit-config.yaml`: ruff, mypy and basic hygiene hooks (`pre-commit install`).

## CI-02 — security scanners

- Scanner versions are locked with hashes in `ci/security-tools.lock` (generated by uv from
  `ci/security-tools.txt`); gitleaks is downloaded by version and checked by SHA-256.
- Trivy's own version is pinned (`TRIVY_VERSION`), not taken as "latest".
- Trivy does not read `requirements.lock`; Python dependency CVEs come from pip-audit.

## CI-03 — image

- `Dockerfile` is two-stage. The builder installs `requirements.lock` into `/opt/venv`;
  the runtime stage gets only the venv and app code.
- Base image `python:3.12-slim` pinned **by digest**.
- Runtime: `apt-get upgrade` for OS fixes newer than the base image, pip/setuptools removed,
  fixed non-root uid/gid 10001, OCI labels (`version`, `revision`, `source`).
- Verified locally: image builds, `/healthz` 200, Docker health "healthy", no pip, uid 10001,
  137 SBOM components, size ≈ 400 MB (most of it: openai, google-genai, fonttools,
  cryptography, pillow).
- Publishing to GHCR with cosign signatures belongs to the CD stage.

## CI-04 — repository rules

- All third-party actions are pinned to a full commit SHA, with the version in a comment.
  `persist-credentials: false` on every checkout. Workflows checked with actionlint and zizmor.
- `.github/dependabot.yml`: weekly PRs for GitHub Actions and the Docker base digest, with a
  cool-down so brand-new releases are not adopted on day one.
- Python packages: Dependabot cannot regenerate uv locks. Monthly (and on a pip-audit alert):

  ```bash
  uv pip compile requirements.txt --universal --python-version 3.12 --generate-hashes --upgrade -o requirements.lock
  uv pip compile requirements-dev.txt --universal --python-version 3.12 --generate-hashes --upgrade -o requirements-dev.lock
  pytest -q --cov && ruff check . && mypy
  ```

- `.github/CODEOWNERS`: both developers (@zhaqsylyqq, @karleone-don) own everything, so
  each reviews the other's PRs; security-sensitive and supply-chain paths are listed separately.

### Owner steps (GitHub settings, repository owner only)

Settings → Branches → Add branch ruleset (or classic protection) for `main`:

1. Require a pull request before merging; required approvals: **1**; dismiss stale approvals
   on new commits; require review from Code Owners.
2. Require status checks to pass: `Lint and types`, `Tests and coverage`,
   `Container image (build, scan, SBOM)`. Require branches to be up to date.
3. Block force pushes and deletions. Do not allow bypass (include administrators).
4. Settings → Code security: enable Dependabot alerts, Dependabot security updates,
   secret scanning and push protection.
5. Settings → Actions → General → Workflow permissions: **Read repository contents**
   (each workflow asks for more only where it needs it).

After the 2-week review, add `SAST, dependencies, secrets, config` to the required checks.
